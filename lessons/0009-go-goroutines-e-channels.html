Go: goroutines e channels

O rendezvous de Ada e o buffer da troca de mensagens, agora em Go: go, canais sem buffer e com buffer, canais unidirecionais e select. Go não caiu em nenhuma das 4 provas; esta lição serve para fechar o conteúdo e para revisar, por comparação, as Lições 6, 7 e 15. Tempo estimado: 25 minutos. "s.N" indica a página de 09c-Go.pdf.

Ver respostas

1. Os três pilares

PilarO que o slide diz
1. Goroutines s.2threads de nível de usuário (user-space threads / lightweight threads), extremamente leves, gerenciadas pela runtime
2. Channels s.3base teórica: o modelo CSP (Communicating Sequential Processes), de Tony Hoare. Os processos não devem compartilhar memória para se comunicar; devem "comunicar-se para compartilhar memória", usando channels
3. Scheduler M:N s.4a runtime mapeia M goroutines (threads de aplicação) em N threads do sistema operacional (kernel threads), otimizando o uso de múltiplos núcleos de CPU

Diferenciais s.4–6: simplicidade (em vez de locks e semáforos, basta escrever go antes de uma função para criar uma nova rotina); segurança (channels atuam como pipelines de dados, evitando race conditions ao garantir que apenas uma goroutine acesse os dados por vez); eficiência (criar e trocar o contexto de uma goroutine custa muito pouco, permitindo milhares de processos simultâneos).

O pilar 2 é a mesma ideia da Lição 6: "não há variáveis compartilhadas" (07, s.9). Em vez de proteger memória compartilhada com semáforos ou monitores, os processos trocam mensagens.

A ligação com a Lição 6 é desta lição.

2. Goroutine e canal sem buffer: o rendezvous de Go

Notação de canal, do slide de Ada 08, s.24: ch <- data envia data pelo canal ch; <- ch recebe do canal. Repare na seta: ela aponta para onde o dado vai.

O exemplo que os slides de Ada usam para comparar as duas linguagens 08, s.26:

AdaGo
task Server is
  entry GetData(Item : out Integer);
end Server;

task body Server is
begin
  accept GetData(Item : out Integer) do
    Item := 42;   -- Rendezvous action
  end GetData;
end Server;
 
func main() {
  // canal é o ponto de rendezvous
  getData := make(chan int)
  go func() {
    // equivalente à task Server
    getData <- 42   // equivalente ao Accept
  }()
  data := <-getData
  // Cliente bloqueia até servidor enviar
  fmt.Println(data)
}

08, s.26 (comentários do slide).

AdaGo 08, s.24–25
taskgoroutine (go function())
entry / acceptenvio (ch <- data) e recebimento (<- ch) num canal não bufferizado
Ada usa entriesGo usa canais
Bloqueio: o rendezvous de Ada e os canais não bufferizados de Go bloqueiam até que as duas partes estejam prontas.

Passo a passo do código Go acima:

tmaingoroutine
1make(chan int): cria o canal, sem buffer—
2go func() {…}(): cria a goroutine e seguecomeça a rodar
3data := <-getData: ninguém enviou ainda, bloqueia…
4recebe 42; as duas seguemgetData <- 42: main já está esperando, o encontro acontece
5imprime 42termina

Tabela desta lição. Se a goroutine chegasse ao envio antes de main chegar ao recebimento, seria ela a bloquear: "bloqueiam até que as duas partes estejam prontas" (08, s.25).

O slide 12 tem outro exemplo do mesmo tipo, cortado no fim: uma goroutine imprime "Sending...", faz ch <- "hello" (comentário do slide: "envia quando um processo puder receber") e só depois imprime "Sent!" s.11–12. Ou seja: "Sent!" só aparece depois que alguém recebeu.

3. Canais com buffer

// Cria um buffer para 2 strings
ch := make(chan string, 2)

ch <- "mensagem 1"
ch <- "mensagem 2"   // Não bloqueia
// ch <- "mensagem 3"   // Bloquearia

s.9.

Com buffer de tamanho 2, os dois primeiros envios não esperam ninguém; o terceiro bloquearia, porque o buffer está cheio. É a comunicação assíncrona com buffer da Lição 6 ("se o buffer estiver cheio o processo poderá ser bloqueado", 07, s.11), e o mesmo comportamento do produtor com vagas = 0 na Lição 3.

A ligação com as Lições 3 e 6 é desta lição.

Prática 1 · Bloqueia ou não?

Cada linha é independente. Ninguém está recebendo do canal, a não ser que a linha diga.

#SituaçãoO envio…

2o mesmo canal, depois de 2 envios, um 3º ch <- "c"
3ch := make(chan int) (sem buffer), depois ch <- 1
4sem buffer, e outra goroutine já está esperando em <-ch; agora ch <- 1

4. Canais unidirecionais

Canais podem ser bidirecionais (chan) ou unidirecionais (chan<- ou <-chan). O compilador impede enviar para um canal de recebimento ou receber de um canal de envio, o que evita erros como tentar ler de um canal que deveria ser apenas para escrita s.7. Exemplos do slide 8:

comm     := make(chan string)     // bidirecional
keyboard := make(<-chan int)      // só recebimento
screen   := make(chan-> int)      // como está no slide

s.8. Os comentários "bidirecional" e "só recebimento" são desta lição, pelo nome (do teclado só se lê).

Atenção ao slide 8. screen está escrito com chan->, mas o próprio slide 7 diz que as formas unidirecionais são chan<- e <-chan. Pelo slide 7, o canal da tela (só envio) seria chan<- int. Parece erro de digitação.

Boa prática: usar canais unidirecionais. Gera erro de compilação se tentar enviar ou receber num canal que não suporta a operação; funciona como documentação; facilita legibilidade e manutenção s.10.

5. select

select {
case msg1 := <-ch1:
    fmt.Println(msg1)
case msg2 := <-ch2:
    fmt.Println(msg2)
case <-time.After(2*time.Second):
    fmt.Println("Timed out")
//default: No message available
//    fmt.Println("No message")
}

s.13–14, com a indentação desta lição. A linha default está comentada no slide.

Lendo o código (os slides não descrevem a semântica): o select espera uma de várias alternativas. Se chega mensagem em ch1, imprime msg1; se chega em ch2, imprime msg2; se passam 2 segundos sem nada, imprime "Timed out". Com o default descomentado, se não houver mensagem disponível na hora, imprime "No message" sem esperar.

E se Go aparecer na questão 5?

A tabela de 2026 Q5 não tem Go. Se uma variante da questão incluir Go, pelos slides: canais sem buffer bloqueiam até as duas partes estarem prontas, como o rendezvous (08, s.25), ou seja, comunicação síncrona; canais com buffer não bloqueiam enquanto há espaço (s.9), o que é comunicação assíncrona com buffer (07, s.11). Go evita locks e semáforos (s.4–5), então "monitores" seria "não".
