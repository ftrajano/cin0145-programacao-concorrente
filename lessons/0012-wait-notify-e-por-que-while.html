wait, notify e por que while

1. Dois motivos diferentes para esperar

Na lição 11, uma thread t esperava por outra thread u por causa do lock: u estava dentro de um método sincronizado e t queria entrar em um método sincronizado do mesmo objeto.

O material apresenta um segundo motivo. t tem que esperar por u quando a semântica da aplicação exige que uma operação de t só seja executada em condições que podem ser garantidas por uma operação de u. Nesse caso quem pede a espera é a própria aplicação, e a ferramenta é wait.

lock do objetoa linguagem, sozinhasynchronized
uma condição da aplicaçãoa aplicação, pedindowait + notify/notifyAll

2. O exemplo: não debitar além do saldo

A regra de negócio: um débito maior que o saldo não dá erro, ele espera até haver saldo. Quem pode criar essa condição é um crédito, executado por outra thread.

synchronized void debitar(double v) {
  while (saldo < v) {
    wait();
  }
  saldo = saldo - v;
}
synchronized void creditar(double v) {
  saldo = saldo + v;
  notifyAll();
}

wait() interrompe a execução do método e da thread associada. A thread só volta a executar quando notificada por outra thread. notifyAll() avisa a todas as threads que estavam esperando para executar um método do mesmo objeto (this).

11-Concorrencia.pdf, slides 31 e 33.

3. As três regras do wait

  1. Só pode ser chamado dentro de um método synchronized.
  2. Coloca a thread que o executou para esperar por uma notificação.
  3. Libera a restrição de sincronização: outro método sincronizado pode começar a executar no mesmo objeto.

A regra 3 é a que faz o exemplo funcionar. Se o debitar dormisse segurando o lock, o creditar (também synchronized) nunca conseguiria entrar e o saldo nunca aumentaria.

11-Concorrencia.pdf, slide 34.

11-Concorrencia.pdf, slide 35.

5. Por que while e não if

A notificação avisa que talvez seja possível fazer o débito, mas não garante. A thread acordada precisa testar de novo. Com while, ela volta ao teste. Com if, ela segue direto para saldo = saldo - v.

Um caso concreto: saldo 0, duas threads tentando debitar 50 e as duas dormindo no wait. Chega um crédito de 60 e o notifyAll acorda as duas. A primeira a pegar o lock debita e o saldo fica em 10. A segunda:

ComO que a segunda thread fazSaldo final
whiletesta 10 < 50, é verdadeiro, volta a dormir10
ifnão testa de novo e debita−40

11-Concorrencia.pdf, slide 32. O caso com dois débitos de 50 e crédito de 60 foi montado para esta lição.

6. Cuidado com concorrência

Os mecanismos de sincronização diminuem a eficiência do sistema e podem complicar o código. E dois estados ruins passam a ser possíveis:

Deadlock: todas as threads paradas, uma esperando pela outra.

Livelock: threads executando, mas sem gerar nada que possa ser observado pelo usuário.

Decore essas duas frases. A questão 1 da prova usa quase as mesmas palavras.

    code/0003/Conta3.java tem exatamente o cenário do simulador: D1 e D2 debitam 50 e C credita o valor passado na linha de comando. O programa imprime o que cada thread faz, o saldo final e se D1 ou D2 continuam esperando. As linhas com Thread.sleep e isAlive não estão no material; servem só para a demonstração e estão marcadas no código.
    

    O programa completo, como exemplo resolvido. Repare que Conta é exatamente a da seção 2, só com mensagens impressas, e que Debito e Credito seguem o padrão da lição 11.
    

    class Conta {
  private double saldo = 0;

  synchronized void debitar(String quem, double v) throws InterruptedException {
    while (saldo < v) {                 // <- Etapa 3: troque while por if
      System.out.println(quem + ": saldo " + saldo + " < " + v + ", vou esperar (wait)");
      wait();
      System.out.println(quem + ": fui notificada, saldo agora " + saldo);
    }
    saldo = saldo - v;
    System.out.println(quem + ": debitei " + v + ", saldo agora " + saldo);
  }

  synchronized void creditar(double v) {
    saldo = saldo + v;
    System.out.println("C: creditei " + v + ", saldo agora " + saldo);
    notifyAll();                        // <- Etapa 2: troque por notify()
  }

  synchronized double getSaldo() { return saldo; }
}

class Debito extends Thread {
  private Conta conta; private double val; private String nome;
  Debito(String n, Conta c, double v) { nome = n; conta = c; val = v; }
  public void run() {
    try { conta.debitar(nome, val); } catch (InterruptedException e) {}
  }
}

class Credito extends Thread {
  private Conta conta; private double val;
  Credito(Conta c, double v) { conta = c; val = v; }
  public void run() { conta.creditar(val); }
}

public class Conta3 {
  public static void main(String[] args) throws InterruptedException {
    double credito = Double.parseDouble(args[0]);
    Conta c = new Conta();
    Thread d1 = new Debito("D1", c, 50);
    Thread d2 = new Debito("D2", c, 50);
    d1.start(); d2.start();

    // Fora do material, só para a demonstração: dar tempo para D1 e D2
    // chegarem ao wait() antes do crédito.
    Thread.sleep(300);

    Thread cr = new Credito(c, credito);
    cr.start();
    cr.join();

    // Fora do material: em vez de join() nas threads de débito (que poderia
    // esperar para sempre), espera um pouco e mostra quem ainda está parada.
    Thread.sleep(300);
    System.out.println("--> saldo final: " + c.getSaldo());
    System.out.println("--> D1 ainda esperando? " + d1.isAlive());
    System.out.println("--> D2 ainda esperando? " + d2.isAlive());
    System.exit(0);
  }
}

    Questão 7 (2,2 pontos). O problema dos Leitores e Escritores permite que vários Leitores leiam os dados ao mesmo tempo, desde que nenhum Escritor esteja escrevendo. Já os Escritores só podem executar sozinhos, sem outros leitores ou escritores ao mesmo tempo. O código abaixo implementa início e fim de leitura (chamados pelos Leitores) e início e fim de escrita (chamados pelos Escritores).
    

    Da forma como está, o código apresenta algum problema se tivermos um grande número de Leitores e um único Escritor? Se for preciso corrigir, indique as modificações necessárias.
    

    class RWMonitor {
  private String dado = "Conteúdo Inicial";
  private int numeroLeitores = 0;
  private boolean escritorAtivo = false;

  public void iniciarLeitura(String nomeLeitor) throws InterruptedException {
    while (escritorAtivo) {
      wait();
    }
    numeroLeitores++;
    System.out.println(nomeLeitor + " entrou. Leitores ativos: " + numeroLeitores);
  }

  public synchronized void terminarLeitura(String nomeLeitor) {
    numeroLeitores--;
    System.out.println(nomeLeitor + " saiu. Leitores ativos: " + numeroLeitores);
    if (numeroLeitores == 0) {
      notifyAll();
    }
  }

  public void iniciarEscrita(String nomeEscritor) throws InterruptedException {
    while (numeroLeitores > 0 || escritorAtivo) {
      wait();
    }
    escritorAtivo = true;
    System.out.println(nomeEscritor + " começou a escrever.");
  }

  public synchronized void terminarEscrita(String nomeEscritor) {
    escritorAtivo = false;
    System.out.println(nomeEscritor + " terminou de escrever.");
    notify();
  }

  public String getDado() { return this.dado; }
  public void setDado(String novoDado) { this.dado = novoDado; }
}

Respostas da recuperação inicial: (1) Só um deles executa por vez naquele objeto; o outro espera. (2) Entre a leitura e a escrita de uma thread, a outra pode fazer um ciclo inteiro: não há race condition, mas pode haver interferência. (3) start() inicia; join() espera o término. (4) O interpretador, de forma arbitrária.
