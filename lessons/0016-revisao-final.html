2 Prova 2 · Questão 1 · 3,0

Soluções de problemas envolvendo concorrência devem, idealmente, satisfazer a um conjunto de características/propriedades para que sejam consideradas satisfatórias. Indique/explique quais são essas características, indicando se são essenciais ou apenas importantes/desejáveis em alguns casos.

Mostrar resposta modelo
  • Exclusão mútua: instruções das seções críticas de dois ou mais processos não podem executar ao mesmo tempo (03, s.2).
  • Parar fora não atrapalha: um processo pode parar fora da região crítica sem interferir nos outros.
  • Ausência de deadlock: se processos tentam entrar, um deles deve conseguir.
  • Ausência de starvation: se um processo quer entrar, em algum momento entrará.
  • Sem contenção: sem disputa, entra com overhead mínimo (03, s.3–5).
  • Essenciais × desejáveis: exclusão mútua é o que o programa "deve" satisfazer; deadlock "não pode" e starvation "não deve" acontecer; a sem contenção é sobre eficiência. Os slides não classificam explicitamente: diga isso.

4 Prova 1 · Questão 5 · 2,0

Indique se a solução abaixo para o problema dos leitores e escritores (a) garante exclusão mútua, (b) garante ausência de starvation. Justifique e, caso haja problemas, indique a correção.

Monitor Reader_Writer_Monitor {
  int Readers = 0;
  BOOL Writing = False;
  condition OK_to_Read, OK_to_Write;
  void Start_Read {
    while (Writing) {wait(OK_to_Read);};
    Readers = Readers + 1;
  }
  void End_Read {
    Readers = Readers − 1;
    if (Readers==0) {signal(OK_to_Write);};
  }
  void Start_Write {
    if (Readers > 0 || Writing) {wait(OK_to_Write);};
    Writing = True;
  }
  void End_Write {
    Writing := False;
    signal(OK_to_Write);
    signal_all(OK_to_Read);
  }
}
Mostrar resposta modelo
  • (a) A ideia está certa, mas Start_Write usa if: o escritor acordado não testa de novo. Se outro processo entrar no monitor entre o signal e a volta do escritor, ele escreve mesmo assim. Correção: while.
  • Ressalva: os slides não dizem se o acordado roda imediatamente; com while fica garantido em qualquer caso.
  • (b) Não garante: leitores novos entram mesmo com escritor esperando (Start_Read só testa Writing). Se Readers nunca chega a 0, o escritor nunca é acordado: starvation (03, s.5).
  • Correção (ideia): leitor novo espera se há escritor esperando: while (Writing || !empty(OK_to_Write)) (05, s.12).

6 Prova 1 · Questão 3 · 2,0

Descreva o funcionamento de rendezvous. Como o processo servidor pode se comportar ao receber várias solicitações ao mesmo tempo? Quais as vantagens desse mecanismo de programação, e por quê?

Mostrar resposta modelo
  • Funcionamento: comunicação síncrona, sem buffer; o primeiro a chegar espera o outro. A calling task passa os in e espera; a accepting task executa o corpo do accept; os out voltam; as duas seguem (08, s.3, 7).
  • Várias solicitações: as chamadas ficam em filas por entry; com select, as guardas when definem as alternativas abertas; atende a primeira de uma das filas; se todas vazias, suspende; else/delay/terminate (s.10–13).
  • Vantagens: assimétrico, o servidor não precisa conhecer os clientes (bom para servidores, s.4); sincroniza e troca dados numa operação, nas duas direções (s.9); implementa RPC (s.14); sem variáveis compartilhadas, guardas no lugar de wait/signal; expressivo (semáforo, timeout, polling).

10 Prova 1 · Questão 4 · 2,0

Para a implementação de um projeto é dada a você a oportunidade de decidir se a comunicação entre os processos deverá ser implementada usando monitores ou usando um mecanismo baseado em troca de mensagens. Que aspectos do problema podem levar você a optar por uma solução ou pela outra?

Mostrar resposta modelo
  • Hardware: monitor pressupõe memória compartilhada; com processadores e memória fisicamente distribuídos, só rede, a escolha é mensagens (07, s.2–4; 05, s.5).
  • Natureza da interação: proteger dados compartilhados (buffer, leitores-escritores) → monitor, que concentra dados e operações e dá exclusão mútua implícita (05, s.3–6); processos independentes trocando pedidos (clientes, servidores, filtros, peers) → mensagens (07, s.20).
  • Sincronização: monitor usa variáveis de condição; mensagens sincronizam pelo próprio receive (07, s.8), síncrona ou assíncrona (s.10–12).
  • Flexibilidade: mensagens sem identificação fixa permitem adicionar/remover processos dinamicamente (07, s.15, 18).

12 Prova 3 · Questão 1 · 2,5

O que é o problema da exclusão mútua? Quando precisamos nos preocupar com ele? Como ele é resolvido através de Monitores?

Mostrar resposta modelo
  • O problema: N processos em laço com seção não crítica e crítica; instruções das seções críticas não podem executar ao mesmo tempo; sem deadlock, sem starvation, parar fora não atrapalha (03, s.2–5).
  • Quando: sempre que processos compartilham recursos; comandos não são atômicos e se intercalam de forma arbitrária, gerando interferência (11, s.5, 9, 12). Exemplo: creditar(100) || debitar(80).
  • Com monitores: dados e operações encapsulados (ADT); processos só chamam procedimentos do monitor (05, s.3–5); exclusão mútua implícita, sem pré/pós-protocolo (s.6); variáveis de condição com wait/signal para esperar condições (s.12).

13 Prova 2 · Questão 2 · 3,0

Como poderia ser implementada uma solução para o problema dos filósofos em uma linguagem distribuída (por exemplo utilizando rendez-vous em Ada)? Considere que um processo separado controla os garfos e os demais processos são filósofos. Indique como se comporta sua solução em relação às características desejadas (questão anterior).

Mostrar resposta modelo
  • Estrutura: uma task Garfos guarda Livre(0..4); o filósofo i pede os garfos i e (i+1) mod 5 juntos (Garfos.Pegar_i) e depois Garfos.Soltar(i).
  • select com guardas: when Livre(i) and Livre((i+1) mod 5) => accept Pegar_i, marca os dois como ocupados; accept Soltar(I) libera (08, s.10–13).
  • Exclusão mútua: sim, só a task Garfos mexe no estado, um rendezvous por vez.
  • Deadlock: não há, ninguém segura um garfo esperando o outro (compare com a solução 1 dos semáforos).
  • Starvation: não garantida, os vizinhos podem se revezar; o select atende "a primeira de uma das filas" (s.12).
  • Sem contenção: sim, guarda aberta, atendido na hora.

14 2026-1 · Questão 7 · 2,2

Leitores e escritores em Java. Da forma como está, o código apresenta algum problema se tivermos um grande número de processos Leitores e um único processo Escritor? Se for preciso corrigir algo, indique as modificações.

class RWMonitor {
  private String dado = "Conteúdo Inicial";
  private int numeroLeitores = 0;
  private boolean escritorAtivo = false;

  public void iniciarLeitura(String nomeLeitor) throws InterruptedException {
    while (escritorAtivo) {
      wait();
    }
    numeroLeitores++;
    System.out.println(nomeLeitor + " entrou. Leitores ativos: " + numeroLeitores);
  }

  public synchronized void terminarLeitura(String nomeLeitor) {
    numeroLeitores--;
    System.out.println(nomeLeitor + " saiu. Leitores ativos: " + numeroLeitores);
    if (numeroLeitores == 0) {
      notifyAll();
    }
  }

  public void iniciarEscrita(String nomeEscritor) throws InterruptedException {
    while (numeroLeitores > 0 || escritorAtivo) {
      wait();
    }
    escritorAtivo = true;
    System.out.println(nomeEscritor + " começou a escrever.");
  }

  public synchronized void terminarEscrita(String nomeEscritor) {
    escritorAtivo = false;
    System.out.println(nomeEscritor + " terminou de escrever.");
    notify();
  }

  public String getDado() { return this.dado; }
  public void setDado(String novoDado) { this.dado = novoDado; }
}
Mostrar resposta modelo
  • Sim, há problema.
  • iniciarLeitura e iniciarEscrita chamam wait() sem ser synchronized: wait só pode ser chamado dentro de método synchronized. Correção: acrescentar synchronized (11, s.34).
  • Sem synchronized, testes e atualizações de numeroLeitores/escritorAtivo podem se intercalar: interferência.
  • terminarEscrita usa notify(), que acorda só uma thread arbitrária; com muitos leitores esperando, os outros ficam parados. Correção: notifyAll() (s.35).
  • Já estava certo: os while e o notifyAll de terminarLeitura.

15 Prova 1 · Questão 1 · 2,0

Quais as principais dificuldades para o desenvolvimento de programas concorrentes ou distribuídos? Por que eles são mais difíceis de desenvolver que os programas sequenciais?

Mostrar resposta modelo
  • Comandos não atômicos: até saldo = saldo + 5 executa por partes que se intercalam (11, s.5–6).
  • Não determinismo: a intercalação é arbitrária, o mesmo programa dá resultados diferentes (20, −80 ou 100) (s.9, 11).
  • Interferência em recursos compartilhados (s.12).
  • Controle extra: controlar acesso, proibir sequências, sincronizar (s.13).
  • Custo e novos erros: sincronização reduz eficiência; deadlock e livelock (s.36).
  • Por que mais difícil: é preciso raciocinar sobre todas as intercalações, não sobre uma sequência. Distribuídos: sem memória compartilhada, só mensagens (07, s.3, 9).

17 Prova 2 · Questão 3 · 3,0

Descreva o problema dos leitores e escritores, e sua solução usando monitores.

Mostrar resposta modelo
  • Problema: leitores podem ler juntos; escritores precisam excluir todos, leitores e escritores (05, s.14). Laços Start_Read; Read; End_Read e Start_Write; Write; End_Write (s.15–16).
  • Monitor: os 4 procedimentos no monitor, exclusão mútua implícita; estado Readers, Writing; condições OK_to_Read, OK_to_Write (s.16–17).
  • Cada procedimento: Start_Read espera enquanto Writing e incrementa; End_Read decrementa e, se 0, signal(OK_to_Write); Start_Write espera se há leitores ou escrita e marca Writing; End_Write desmarca, signal(OK_to_Write) e signal_all(OK_to_Read) (s.17–19).
  • wait/signal: wait suspende na fila FIFO e libera o monitor; signal acorda o primeiro (s.12).
  • Extra que valoriza: o if de Start_Write deveria ser while; starvation de escritores.

18 Prova 3 · Questão 4 · 2,5

Como você projetaria um servidor web concorrente (com múltiplos threads)? Você detecta algum problema de exclusão mútua? Explique por quê.

Mostrar resposta modelo
  • Projeto: uma thread principal recebe os pedidos e cria uma thread para cada pedido (ou reaproveita threads), que atende e responde; em Java, threads criadas e iniciadas com start() (Lição 11). Criar processos dinamicamente conforme a demanda é a "razão" de balanceamento de carga (07, s.18).
  • Há problema de exclusão mútua quando as threads compartilham recursos que são alterados: comandos não são atômicos e se intercalam de forma arbitrária, gerando interferência (11, s.5, 9, 12). Exemplos de recurso compartilhado num servidor: um contador de acessos, um cache de páginas, um arquivo de log.
  • Solução: acesso a esses recursos em métodos synchronized (11, s.14) ou num monitor (05, s.6). Se os dados são muito lidos e pouco alterados (páginas, cache), é o padrão leitores-escritores (05, s.14).
  • Por quê: se cada thread só lê dados que ninguém altera, não há interferência; o problema aparece só onde há escrita compartilhada.
  • Resposta construída para esta revisão a partir dos slides citados; os slides não falam de servidor web. Os exemplos (contador, cache, log) são suposições sobre servidores web.

20 Prova 2 · Questão 4 · 1,0

Como é possível controlar exclusão mútua em um sistema distribuído?

Mostrar resposta modelo
  • Nenhum slide trata disto diretamente.
  • O mais próximo no material: sem memória compartilhada, não dá para usar semáforos ou monitores comuns; a exclusão mútua tem de vir das mensagens (07, s.3, 9).
  • Processo coordenador: uma task que simula um semáforo com rendezvous (loop accept Wait; accept Signal; end loop, 08, s.14–15); cada processo chama Wait antes da região crítica e Signal depois.
  • Ou um servidor dono do recurso: só ele mexe nos dados, e os pedidos são atendidos um por vez (servidores de Erlang, 12, s.15–16; Linda, contador "Next" removido com Input, 09b, s.10).
