Lição 14 · Concorrência em Java

wait e notify, passo a passo

O mesmo assunto da lição 12, agora explicado com tabelas: uma coluna por thread, uma linha por instante. Tempo estimado: 25 minutos. As marcações "s.N" indicam só de onde veio cada afirmação (11-Concorrencia.pdf).

Aquecimento, de memória (sem rolar a página):

  1. Depois de a.start(), o main espera ou segue em frente?
  2. Quem cria a concorrência: extends Thread + start() ou synchronized? E quem a controla?

Respostas: 1. segue em frente; quem espera é o join(). 2. Thread + start() cria; synchronized controla.

1. O problema: um débito que precisa esperar

Até aqui, uma thread só esperava por outra por causa do lock: só um método synchronized por vez no mesmo objeto. Agora aparece um segundo motivo: a regra da aplicação. Um débito maior que o saldo não dá erro; ele espera até alguém creditar. s.29–31

O código, com as linhas numeradas para as tabelas:

synchronized void debitar(double v) {    synchronized void creditar(double v) {
d1   while (saldo < v)                    c1   saldo = saldo + v;
d2       wait();                          c2   notifyAll();
d3   saldo = saldo - v;                  }
}

Três regras do material, que as tabelas vão mostrar acontecendo:

ComandoO que faz
wait()A thread dorme e solta o lock. Só pode ser chamado dentro de método synchronized.s.31, 34
notifyAll()Acorda todas as threads que dormem no objeto.s.33, 35
notify()Acorda só uma, escolhida de forma arbitrária.s.35

Duas palavras das tabelas. Nesta lição, "dormindo" e "esperando o lock" são coisas diferentes:

Nas tabelasO que causouO que tira a thread desse estadoSegura o lock?
dormindoa própria thread executou wait()outra thread chamar notify()/notifyAll()não, soltou
esperando o lockquer entrar (ou voltar) num método synchronized e outra thread está dentroa outra thread sair do método (ou chamar wait())não, ainda não tem

"Dormindo" é palavra desta lição; o slide diz que o wait "interrompe a execução do método e da thread" e que ela "só volta a executar quando notificada" (s.31). Os dois motivos de espera são os de s.29–30.

2. Tabela resolvida: uma thread debita, outra credita

Saldo inicial 0. A thread D chama debitar(50); a thread C chama creditar(60). D chega primeiro. Leia linha por linha.

tThread D · debitar(50)Thread C · creditar(60)saldolock com
1entra em debitar—0D
2d1: 0 < 50? sim—0D
3d2: wait() → dorme e solta o lock—0ninguém
4dormindoentra em creditar (só porque o lock está livre)0C
5dormindoc1: saldo = 0 + 6060C
6acorda, mas espera o lockc2: notifyAll()60C
7esperando o locksai de creditar60ninguém
8pega o lock e volta para d1: 60 < 50? não—60D
9d3: saldo = 60 − 50—10D
10sai de debitar—10ninguém

As linhas em destaque são as quatro coisas que você precisa ver:

  • t3–t4: C só consegue entrar porque o wait soltou o lock (s.34). Se D dormisse segurando o lock, C ficaria esperando D, e D esperando C: as duas paradas, uma esperando a outra. Isso é exatamente a definição de deadlock (s.36).
  • t6: acordar não é o mesmo que continuar. D ainda precisa pegar o lock, porque debitar é synchronized e C ainda está dentro de creditar.
  • t8: por causa do while, D testa de novo antes de debitar.

Cenário montado para esta lição a partir do código de s.31 e s.33. A conclusão sobre deadlock na t3–t4 é uma aplicação de s.34 e s.36.

Prática 1 · Complete a tabela: if no lugar de while

Agora há duas threads debitando, D1 e D2, cada uma debitar(50), e as duas já estão dormindo no wait(). C chama creditar(60). A diferença: alguém trocou o while por if:

d1   if (saldo < v)
d2       wait();
d3   saldo = saldo - v;

Preencha as células e clique em Conferir. Os números são saldos.

0dormindodormindo—0
1dormindodormindoc1: saldo = 0 + 60
2C chama notifyAll(). Quem acorda? c2: notifyAll(), depois sai60
3pega o lock. Com if, volta a testar? esperando o lock—60
4d3: saldo = 60 − 50, saiesperando o lock—

Agora imagine o mesmo cenário com while. Na t5, D2 volta ao teste 10 < 50. O que acontece e qual é o saldo final?

tD2, com whilesaldo

Regra: a notificação avisa que talvez seja possível continuar, mas não garante; por isso o teste é um while (s.32). O cenário D1/D2/crédito 60 foi montado para a lição 12.

Prática 2 · Complete a tabela: notify no lugar de notifyAll

Código correto, com while, mas creditar usa notify(). D1 e D2 dormindo, cada uma querendo debitar 50. C credita 100, dinheiro suficiente para as duas.

tO que acontecesaldo
1C: saldo = 0 + 100
2C: notify(). Quantas threads acordam? 100
3A acordada testa 100 < 50 (não) e debita
4E a outra thread? 50

Com notifyAll(), as duas acordam, cada uma testa o while na sua vez, e o saldo final é 0. Esse é o erro do notify: há dinheiro, mas a thread que poderia usá-lo ficou dormindo. s.35; cenário da lição 12.

3. Deadlock e livelock

Os mecanismos de sincronização diminuem a eficiência e podem complicar o código. E criam dois estados ruins (s.36):

As threads estão…Produzem algo observável?Definição do slide
Deadlockparadasnãotodas as threads paradas, uma esperando pela outra
Livelockexecutandonãothreads executando, mas sem gerar nada que possa ser observado pelo usuário

A diferença está toda na segunda coluna. Você já viu um deadlock nesta lição: o "e se o wait não soltasse o lock?" da seção 2.
