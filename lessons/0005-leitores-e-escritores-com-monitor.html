Leitores e escritores com monitor (e o fim do arquivo 05)

O problema que caiu em três das quatro provas, com o monitor dos slides linha por linha e as duas questões antigas respondidas. No fim, o resto do arquivo 05: a emulação de semáforos por monitores e o barbeiro que dorme. Tempo estimado: 45 minutos. "s.N" = 05-monitores.pdf, salvo indicação.

Aquecimento da lição 4, de memória: o que signal(C) faz quando a fila de C está vazia? E signal_all(C)?

Ver respostas

Com a fila vazia, signal não faz nada (s.12). signal_all acorda todos os processos suspensos em C (s.14).

1. O problema

Vários processos acessam os mesmos dados. Uns só leem, outros escrevem. s.14

QuemRegra
Leitoresnão precisam se excluir mutuamente: vários podem ler ao mesmo tempo
Escritoresprecisam excluir todos os outros processos, leitores e escritores

É uma exclusão mútua "seletiva": nem todo mundo exclui todo mundo. Cada processo é um laço que chama o monitor antes e depois de usar os dados s.15–16:

Reader() {                       Writer() {
  while (TRUE) {                   while (TRUE) {
    Start_Read;                      Start_Write;
    Read_the_Data;                   Write_the_Data;
    End_Read;                        End_Write;
  }                                }
}                                }

2. O monitor dos slides

Duas variáveis de status e duas variáveis de condição s.16–17:

VariávelSignificado
Readersnúmero de leitores lendo agora
Writingtrue quando um processo está escrevendo
OK_to_Readfila onde leitores esperam
OK_to_Writefila onde escritores esperam
Monitor Reader_Writer_Monitor {
  int Readers = 0;
  BOOL Writing = False;
  Condition OK_to_Read, OK_to_Write;

  void Start_Read {
r1  while (Writing) {wait(OK_to_Read);};
r2  Readers = Readers + 1;
  }
  void End_Read {
e1  Readers = Readers - 1;
e2  if (Readers == 0) {signal(OK_to_Write);};
  }
  void Start_Write {
w1  if (Readers > 0 || Writing) {wait(OK_to_Write);};    ← if, não while!
w2  Writing = True;
  }
  void End_Write {
f1  Writing := False;
f2  signal(OK_to_Write);
f3  signal_all(OK_to_Read);
  }
}

s.17–19, copiado como está, inclusive o := em f1. Este é exatamente o código da Prova 1, questão 5.

Em palavras:

  • Start_Read: o leitor só espera se alguém está escrevendo. Se há outros lendo, ele entra junto.
  • End_Read: o último leitor a sair (Readers == 0) acorda um escritor.
  • Start_Write: o escritor espera se há alguém lendo ou escrevendo.
  • End_Write: acorda um escritor e todos os leitores que esperam.

Questão da prova: Prova 1, questão 5 (com resposta)

Prova 1, questão 5 (2,0 pontos). Indique se a solução abaixo para o problema dos leitores e escritores (a) garante exclusão mútua, (b) garante ausência de starvation. Justifique sua resposta e, caso haja problemas, indique sua correção.

O código é o monitor da seção 2, sem nenhuma diferença.

Provas-Concorrencia-antigas.pdf, Prova 1.

Resposta (derivada do material; não é o gabarito oficial)

(a) Exclusão mútua: depende do if em Start_Write. A ideia está certa: o leitor espera enquanto há escrita (r1), e o escritor espera enquanto há leitura ou escrita (w1). O problema é que w1 usa if, então o escritor acordado não testa a condição de novo. Se, entre o signal e o momento em que o escritor volta a executar, outro processo entrar no monitor, o escritor segue para w2 mesmo assim. Exemplo: o último leitor sai e faz signal(OK_to_Write); antes de W voltar a executar, chega um leitor novo, vê Writing falso e entra (Readers = 1); W volta e, sem testar, faz Writing = True. Resultado: um escritor e um leitor ao mesmo tempo.

Correção: trocar o if de w1 por while, como já é feito em Start_Read e no produtor-consumidor (s.8–9). Com while, o processo acordado testa a condição de novo antes de seguir.

Ressalva: os slides não dizem se o processo acordado por signal executa imediatamente ou só depois. Se executar imediatamente, ninguém consegue entrar no meio e o if funciona. Na prova, vale dizer as duas coisas: "com if, a exclusão mútua depende de o processo acordado executar imediatamente; com while, fica garantida em qualquer caso".

(b) Ausência de starvation: não garante. Os escritores podem sofrer starvation. Start_Read só testa Writing, então um leitor novo entra mesmo com um escritor esperando. Se os leitores se revezarem sem que Readers chegue a 0, o escritor nunca é acordado, porque só o último leitor a sair faz signal(OK_to_Write) (e2). É exatamente a tabela da Prática 1. Pela definição, há starvation: o escritor quer entrar e nunca entra (03, s.5).

Correção (ideia): um leitor novo não deve entrar se houver escritor esperando. O monitor tem a operação certa para isso, empty(C) (s.12): em Start_Read, esperar também enquanto !empty(OK_to_Write):

void Start_Read {
  while (Writing || !empty(OK_to_Write)) {wait(OK_to_Read);};
  Readers = Readers + 1;
}

Essa correção foi montada para esta lição, aplicando s.5 e s.12; não está nos slides. Ela dá preferência aos escritores, e com isso uma sequência contínua de escritores poderia atrasar os leitores. Uma solução totalmente justa precisa alternar a preferência entre os dois grupos ao fim de cada escrita. Na prova, o essencial é apontar quem sofre starvation, mostrar por quê, e indicar a ideia da correção.

Questão da prova: Prova 2, questão 3 (com resposta)

Prova 2, questão 3 (3,0 pontos). Descreva o problema dos leitores e escritores, e sua solução usando monitores.

Resposta modelo (construída só com o material)

O problema. Vários processos compartilham dados. Os leitores apenas leem e não precisam se excluir mutuamente: vários podem ler ao mesmo tempo. Os escritores modificam os dados e precisam excluir todos os outros processos, leitores e escritores (05, s.14). Cada leitor executa em laço Start_Read; Read_the_Data; End_Read, e cada escritor Start_Write; Write_the_Data; End_Write (s.15–16).

A solução com monitor. Os procedimentos Start_Read, End_Read, Start_Write e End_Write ficam num monitor, que garante exclusão mútua implícita entre eles: as variáveis de controle nunca são alteradas por dois processos ao mesmo tempo (s.6). O monitor guarda Readers (número de leitores lendo) e Writing (verdadeiro quando alguém escreve), e tem duas variáveis de condição, OK_to_Read e OK_to_Write (s.16–17).

  • Start_Read: enquanto Writing, espera em OK_to_Read; depois incrementa Readers.
  • End_Read: decrementa Readers; se chegou a 0, faz signal(OK_to_Write) para acordar um escritor.
  • Start_Write: se há leitores (Readers > 0) ou alguém escrevendo, espera em OK_to_Write; depois faz Writing = True.
  • End_Write: faz Writing = False, acorda um escritor com signal(OK_to_Write) e todos os leitores com signal_all(OK_to_Read) (s.17–19).

wait(C) suspende o processo na fila FIFO de C e libera a exclusão mútua do monitor, para que outros possam entrar e mudar a condição; signal(C) acorda o primeiro da fila (s.12).

Observações que valorizam a resposta: o teste de Start_Write deveria ser while, e a solução permite starvation de escritores se os leitores não pararem de chegar (ver a questão anterior).

4. Emulação de semáforos por monitores

Os slides mostram que um monitor consegue fazer o papel de um semáforo: uma variável S e duas operações, P e V, como na Lição 3. Há duas versões s.20–22.

Versão 1 s.20Versão 2 s.21–22
monitor Semaphore_Emulation {
  int S = 0;
  Condition Not_Zero;

  procedure P {
    while (S == 0) {wait(Not_Zero);};
    S = S - 1;
  }
  procedure V {
    S = S + 1;
    signal(Not_Zero);
  }
}
 
monitor Semaphore_Emulation {
  int S = 0;
  Condition Not_Zero;

  procedure P {
    if (S > 0) {S = S - 1;}
    else {wait(Not_Zero);};
  }
  procedure V {
    if (empty(Not_Zero)) {S = S + 1}
    else {signal(Not_Zero)};
  }
}

Código de s.20–22, com a indentação desta lição.

A diferença está no V (leitura desta lição do código):

  • Versão 1: V sempre soma 1 em S e depois acorda alguém. O processo acordado volta ao while, vê S maior que 0 e ele mesmo subtrai 1. É o P da Lição 3 escrito com wait/signal: <await (s > 0) -> s := s – 1> (04, s.8).
  • Versão 2: se há alguém esperando, V não soma 1: só acorda esse processo, e o P dele termina sem subtrair. A "unidade" de S passa direto de quem fez V para quem estava esperando. Se não há ninguém esperando (empty(Not_Zero)), aí sim S aumenta, para o sinal não se perder.

Esse último ponto é a ligação com a Lição 4: signal com a fila vazia não faz nada, enquanto V sempre "guarda" o sinal em S. As duas versões guardam o sinal em S quando ninguém espera, e por isso se comportam como semáforo.

5. O problema do barbeiro que dorme

O último exemplo do arquivo 05 é só descrito, sem código s.23–25:

  • Uma barbearia com duas portas (entrada e saída) e algumas cadeiras de espera.
  • O barbeiro atende um cliente de cada vez. Se faltam clientes, o barbeiro dorme.
  • Se um cliente chega, ele acorda o barbeiro para que corte seu cabelo.
  • O cliente dorme nas cadeiras de espera se o barbeiro está ocupado.

Como modelar: clientes e barbeiros são processos; a barbearia é o monitor; a relação é cliente/servidor, com o barbeiro como servidor. Procedimentos do monitor: get_haircut, get_next_custumer, finished_cut s.24–25. O slide diz ainda que o problema é semelhante a problemas de escalonamento de disco e que é um relacionamento cliente-servidor do tipo rendezvous s.23.

ProcedimentoQuem chamaPara quê
get_haircutclientepedir o corte: acorda o barbeiro ou espera numa cadeira
get_next_custumerbarbeiropegar o próximo cliente; se não há, dorme
finished_cutbarbeiroavisar que terminou o corte, liberando o cliente

Os nomes dos procedimentos são do slide (inclusive a grafia "custumer"). As colunas "Quem chama" e "Para quê" são deduções desta lição a partir dos nomes e da descrição de s.24; os slides não mostram o código.

Por que "rendezvous"? Cliente e barbeiro precisam se encontrar para o corte acontecer: quem chega primeiro espera o outro (o barbeiro dorme sem clientes; o cliente dorme se o barbeiro está ocupado). É a mesma ideia do rendezvous da comunicação síncrona (07, s.10; Lição 7). Isso ajuda na questão P1 Q3 (rendezvous e servidor com várias solicitações): as cadeiras de espera são a fila de pedidos do servidor.
