1. Ada e o rendezvous

Ada foi criada pelo US DOD para ser a linguagem padrão no desenvolvimento de softwares críticos: tipos fortes, packages e suporte direto a concorrência com tasks s.2. Uma task é um processo.

O rendezvous ("encontro") é a comunicação síncrona da Lição 6, sem buffers s.3:

  • duas tasks se encontram num rendezvous para se comunicar, e a primeira a chegar espera pela outra;
  • a accepting task (a que aceita) é a dona do rendezvous;
  • a calling task (a que chama) tem que saber a identidade da accepting task e o nome do local do rendezvous.

É um modelo assimétrico: quem chama sabe com quem fala; quem aceita, não precisa saber quem chama. Por isso é bom para programar processos servidores s.4. O slide 3 também lista o tema "expressividade vs. eficiência".

2. Como se escreve: specification, body, entry, accept

Uma task em Ada tem duas partes s.4–6: a specification, que lista as entries (os "locais de encontro" que a task oferece), e o body, com o código.

task Buffer is                         -- specification
  entry Append (I: in Integer);
  entry Take (I: out Integer);
end Buffer;

task body Buffer is                    -- body
begin
  …
  accept Append(I: in Integer) do
    … corpo do accept
  end Append;
  …
end Buffer;

Buffer.Append(I);                      -- chamada, em outra task

s.5–6, com a indentação e os comentários desta lição.

Notação Ada que aparece nos slides. := é atribuição; -- começa um comentário; mod é o resto da divisão (o % de C); in é parâmetro que entra na accepting task, out é parâmetro que volta para quem chamou. E aqui, diferente do monitor dos slides, a chamada usa ponto: Buffer.Append(I) = entry Append da task Buffer.

A leitura de :=, -- e mod é desta lição, a partir do uso nos slides. in/out: s.7.

O que acontece no rendezvous s.7:

  1. a calling task passa seus parâmetros in para a accepting task e espera o rendezvous se completar;
  2. a accepting task executa os comandos do corpo do accept (até o end);
  3. os parâmetros out são passados de volta à calling task;
  4. o rendezvous terminou, e as duas tasks não estão mais suspensas.

Resumo do slide 9: o rendezvous de Ada é comunicação síncrona e não bufferizada, com identificação assimétrica e fluxo de dados nas duas direções durante o rendezvous (in vai, out volta).

3. O buffer, versão 1: sem select

task body Buffer is
  B: Array (0..N-1) of Integer;
  In_Ptr, Out_Ptr: Integer := 0;
  Count: Integer := 0;
begin
  loop
    accept Append(I: in Integer) do
      B(In_Ptr) := I;
    end Append;
    Count := Count + 1;
    In_Ptr := (In_Ptr + 1) mod N;
    accept Take(I: out Integer) do
      I := B(Out_Ptr);
    end Take;
    Count := Count - 1;
    Out_Ptr := (Out_Ptr + 1) mod N;
  end loop;
end Buffer;

s.8. O slide chama de buffer degenerado (de tamanho 1).

Compare com o monitor da Lição 4: mesmos B, In_Ptr, Out_Ptr, Count. Mas não há wait nem signal: quem espera é quem chega ao encontro primeiro. Por que "degenerado"? Os dois accept estão em sequência: depois de um Append, a task só aceita Take. Então o buffer nunca guarda mais de 1 item, mesmo tendo N posições.

A explicação de "degenerado" é desta lição, lendo o código de s.8.

4. O buffer, versão 2: select com guardas

task body Buffer is …
begin
  loop
    select
      when Count < N =>
        accept Append(I: in Integer) do
          B(In_Ptr) := I;
        end Append;
        Count := Count + 1;
        In_Ptr := (In_Ptr + 1) mod N;
    or
      when Count > 0 =>
        accept Take(I: out Integer) do
          I := B(Out_Ptr);
        end Take;
        Count := Count - 1;
        Out_Ptr := (Out_Ptr + 1) mod N;
    end select;
  end loop;
end Buffer;

s.10–11, com a indentação desta lição.

Semântica do select s.12–13:

  1. as guardas (cláusulas when) são avaliadas, gerando o conjunto de alternativas abertas; tem que haver pelo menos uma, ou um else;
  2. se há tasks em fila esperando por entries em alternativas abertas, o rendezvous é iniciado com a primeira de uma das filas;
  3. se todas as filas das alternativas abertas estão vazias, a accepting task é suspensa até que uma task chame uma dessas entradas; o conjunto de alternativas abertas não muda enquanto isso;
  4. a última alternativa pode ser else …, delay T … ou terminate.

Lendo as guardas: when Count < N = "só aceito Append se há vaga"; when Count > 0 = "só aceito Take se há item". É o papel que vagas/itens tinham na Lição 3 e Not_Full/Not_Empty na Lição 4. Quem chama uma entry fechada fica na fila dela.

A comparação com as Lições 3 e 4 é desta lição.

5. Programando com rendezvous

O slide 14 resume: rendezvous implementa remote procedure call (RPC); delay implementa timeout; else implementa polling; sincronização pode ser feita com corpos de accept vazios s.14. Os exemplos:

ExemploCódigo (resumido)O que faz
Semáforo binário s.14–15loop accept Wait; accept Signal; end loop;Depois de um Wait, a task só aceita Signal. Então um segundo Wait espera até alguém fazer Signal: é o semáforo binário que começa em 1 da Lição 3.
Accepts aninhados s.15–16accept Synch_2 do accept Synch_3; end Synch_2;Sincroniza múltiplas tarefas: T1, a task que chama Synch_2 e a que chama Synch_3 só seguem quando as três se encontraram.
Múltiplos accepts s.17accept E(…) do process odd calls end E; accept E(…) do process even calls end E;A mesma entry com dois tratamentos: as chamadas ímpares (1ª, 3ª, …) pelo primeiro, as pares pelo segundo.
select na calling task s.18select Sensor.Sample(…); or delay 1.0; Notify_Operator; end select;A calling task só pode suspender em uma entry. Se Sensor não aceitar em 1 segundo, desiste e avisa o operador: timeout.
Polling de vários servidores s.19–20select Server_1.E(…); else null; end select; select Server_2.E(…); else null; end select;Alterna a busca: tenta Server_1; se ele não está pronto agora, não espera (else null) e tenta Server_2.
Polling de um servidor s.20select Server_1.E(…); else select Server_2.E(…); else …; end select; end select;Só usa o segundo quando o primeiro falha (não está pronto).

Na coluna "O que faz", estas frases são dos slides: "sincroniza múltiplas tarefas", "a calling task só pode suspender em uma entry", "alterna a busca", "só usa o segundo quando o primeiro falha". O resto é leitura desta lição do código.

6. Arrays de tasks

Ada permite definir um tipo task, como um registro. As operações válidas são entry calls e passagem como parâmetro; cada nova variável declarada cria um novo objeto task; dá para fazer arrays e listas de tarefas s.21:

task type Buffer_Type is …
  entry Append(I: in Integer);
  entry Take(I: out Integer);
end Buffer_Type;

Buffers : array(1..20) of Buffer_Type;      -- 20 buffers, 20 tasks

procedure P(Buff: in Buffer_Type) is
  I : Integer := …;
begin
  Buff.Append(I);           -- call entry in parameter
end P;

Buffers(I+1).Append(E1);    -- direct call
P(Buffers(J));              -- task parameter

s.22–23.

Prática 2 · Exercício do slide 23: leitores e escritores

O slide pergunta: "o que é necessário para corrigir essa implementação do problema dos Leitores e Escritores?" s.23–24

task body Readers_and_Writers is … begin
  accept Start_Write;
  accept End_Write;
  loop
    select
      accept Start_Read …;
    or accept End_Read …;
    or accept Start_Write …;
    or accept End_Write …;
    end select;
  end loop;
end Readers_and_Writers;

Pense antes de abrir: o que impede um leitor de começar enquanto alguém escreve?

Ver uma resposta

Nada impede. Sem guardas, as 4 alternativas estão sempre abertas: um Start_Read pode ser aceito no meio de uma escrita, e dois Start_Write seguidos também. Falta guardar estado (quantos leem, se alguém escreve) e usar guardas when, como no buffer:

task body Readers_and_Writers is
  Readers: Integer := 0;
  Writing: Boolean := False;
begin
  accept Start_Write;
  accept End_Write;
  loop
    select
      when not Writing =>
        accept Start_Read;  Readers := Readers + 1;
    or accept End_Read;     Readers := Readers - 1;
    or when Readers = 0 and not Writing =>
        accept Start_Write; Writing := True;
    or accept End_Write;    Writing := False;
    end select;
  end loop;
end Readers_and_Writers;

Mesmo assim, como no monitor da Lição 5, se sempre houver um leitor lendo, Readers nunca chega a 0 e o escritor pode sofrer starvation.

Esta correção é desta lição (o slide só faz a pergunta), usando apenas construções dos slides: variáveis da task e guardas when (s.10–12).

7. Ponte para Go

Os últimos slides comparam Ada com Go: a task de Ada é como uma goroutine; o par entry/accept é como enviar e receber num canal não bufferizado; nos dois, a comunicação bloqueia até que as duas partes estejam prontas s.24–26. Go é o assunto da Lição 9; aqui basta guardar que o rendezvous aparece de novo lá.

Questão da prova: P1, questão 3 (com resposta)

"Descreva o funcionamento de rendezvous. Como o processo servidor pode se comportar ao receber várias solicitações ao mesmo tempo? Quais as vantagens desse mecanismo de programação, e por que?"

Resposta modelo:

  1. Funcionamento. Rendezvous é comunicação síncrona, sem buffers: duas tasks se encontram para se comunicar e a primeira a chegar espera pela outra. A accepting task (servidor) declara entries e as aceita com accept; a calling task (cliente) chama Servidor.Entry(params). A calling task passa os parâmetros in e espera; a accepting task executa o corpo do accept; os parâmetros out voltam; as duas seguem (s.3, 7).
  2. Várias solicitações ao mesmo tempo. As chamadas ficam em filas, uma por entry. Com select, o servidor avalia as guardas when e obtém as alternativas abertas; se há tasks esperando em alguma delas, atende a primeira de uma das filas; se não há, fica suspenso até chegar uma chamada. Ele atende uma por vez, e as guardas permitem recusar temporariamente pedidos que não podem ser atendidos (ex.: Append com buffer cheio). A última alternativa pode ser else (não esperar), delay T (timeout) ou terminate (s.10–13).
  3. Vantagens, e por quê.
    • Modelo assimétrico: o cliente precisa saber o nome do servidor, o servidor não precisa conhecer os clientes; por isso é bom para programar servidores (s.3–4).
    • Sincronização e troca de dados numa operação só, com dados nas duas direções (in e out) (s.9). Implementa RPC (s.14).
    • Não há variáveis compartilhadas entre as tasks: os dados ficam dentro da task servidora, e só ela mexe neles. As guardas fazem o papel das variáveis de condição, sem wait/signal (s.8–11).
    • É expressivo: simula semáforo, sincroniza várias tarefas, faz timeout e polling (s.14–20).

A frase "não há variáveis compartilhadas… só ela mexe neles" é leitura desta lição dos códigos de s.8–11 e de 07, s.3.

Questão da prova: P2, questão 2 (com resposta)

"Como poderia ser implementada uma solução para o problema dos filósofos em uma linguagem distribuída (por exemplo utilizando rendez-vous em Ada)? Considere que um processo separado controla os garfos e os demais processos são filósofos. Indique como se comporta sua solução em relação às características desejadas de uma solução envolvendo programas concorrentes/distribuídos (questão anterior)."

Resposta modelo. Uma task Garfos guarda o estado dos 5 garfos. O filósofo i usa os garfos i e (i+1) mod 5, como na Lição 3. Cada filósofo pede os dois garfos de uma vez; a guarda só abre o pedido quando os dois estão livres.

task Garfos is
  entry Pegar_0;  entry Pegar_1;  entry Pegar_2;
  entry Pegar_3;  entry Pegar_4;
  entry Soltar(I: in Integer);
end Garfos;

task body Garfos is
  Livre: Array (0..4) of Boolean := (True, True, True, True, True);
begin
  loop
    select
      when Livre(0) and Livre(1) => accept Pegar_0;
           Livre(0) := False;  Livre(1) := False;
    or when Livre(1) and Livre(2) => accept Pegar_1;
           Livre(1) := False;  Livre(2) := False;
    or when Livre(2) and Livre(3) => accept Pegar_2;
           Livre(2) := False;  Livre(3) := False;
    or when Livre(3) and Livre(4) => accept Pegar_3;
           Livre(3) := False;  Livre(4) := False;
    or when Livre(4) and Livre(0) => accept Pegar_4;
           Livre(4) := False;  Livre(0) := False;
    or accept Soltar(I: in Integer) do
           Livre(I) := True;  Livre((I + 1) mod 5) := True;
       end Soltar;
    end select;
  end loop;
end Garfos;

-- filósofo 2 (os outros são iguais, com o próprio número):
loop
  Pensar;
  Garfos.Pegar_2;       -- espera até os garfos 2 e 3 estarem livres
  Comer;
  Garfos.Soltar(2);
end loop;

Código construído por esta lição (os slides não resolvem os filósofos em Ada), com as construções de s.5–13. Há uma entry por filósofo porque cada guarda precisa saber quais garfos testar, e nos slides as guardas usam variáveis da task, como Count (s.10).

Comportamento em relação às propriedades (03, s.2–5; Lição 1):

PropriedadeGarante?Por quê
Exclusão mútua (cada garfo com no máximo um filósofo)simsó a task Garfos mexe em Livre, um rendezvous por vez; um Pegar só é aceito com os dois garfos livres
Ausência de deadlocksimninguém segura um garfo esperando o outro: os dois são pegos juntos. Se há filósofos esperando e ninguém comendo, todos os garfos estão livres e a guarda de algum deles está aberta. Compare com a solução 1 da Lição 3, que dava deadlock
