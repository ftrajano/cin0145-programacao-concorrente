1. O remédio: proibir sequências

A lição 1 terminou com o diagnóstico: interferência acontece quando comandos compartilham recursos e suas partes se intercalam de forma ruim. O material lista o que fazer: controlar o acesso a recursos compartilhados, proibir a realização de determinadas sequências de execução e sincronizar as execuções (uma espera pelo término da outra).

Em Java, a ferramenta para isso é a palavra synchronized.

11-Concorrencia.pdf, slides 13–14.

2. A regra do synchronized

Duas frases resumem o mecanismo. Decore as duas, porque a prova cobra exatamente isso.

Só um método synchronized pode ser executado em um objeto por vez. Os outros ficam esperando.

Vários métodos não sincronizados podem ser executados, no mesmo objeto, ao mesmo tempo que um método synchronized.

Dito de outra forma: uma thread t tem que esperar por uma thread u quando u está executando um método sincronizado e t quer começar a executar um método sincronizado do mesmo objeto. Pode ser o mesmo método ou não.

11-Concorrencia.pdf, slides 14 e 29.

3. A conta, agora segura

Basta marcar os dois métodos. As partes 1-2-3 e A-B-C continuam existindo, mas agora não podem mais se misturar.

class Conta {
  private double saldo = 0;

  synchronized void creditar(double vc) {
1   double tmpc = saldo;
2   tmpc = tmpc + vc;
3   saldo = tmpc;
  }

  synchronized void debitar(double vd) {
A   double tmpd = saldo;
B   tmpd = tmpd - vd;
C   saldo = tmpd;
  }

  synchronized double getSaldo() { return saldo; }
}

Das muitas sequências possíveis de c.creditar(100) || c.debitar(80), só duas sobrevivem:

SequênciaResultado
1 2 3 A B C20
A B C 1 2 320

O programa ficou determinístico: só um resultado é possível. Note que não sabemos qual das duas vai acontecer, e não precisamos saber.

11-Concorrencia.pdf, slides 15–17.

4. Modificador e comando são a mesma coisa

synchronized existe em duas formas, equivalentes:

synchronized void m(...) {
  corpo
}
void m(...) {
  synchronized(this) {
    corpo
  }
}

O comando synchronized(x) { ... } impede a execução simultânea de trechos de código sincronizados no mesmo argumento. Com o modificador, o argumento é sempre this, o próprio objeto. É por isso que a regra da seção 2 fala em "mesmo objeto": duas contas diferentes podem executar creditar ao mesmo tempo sem problema.

11-Concorrencia.pdf, slide 18.

5. Um termo novo: race condition

A partir daqui o material usa a expressão race condition, e vale separá-la de interferência. Os slides não a definem; usam-na em dois comentários, e é desse uso que se tira o sentido:

  • Uma thread lendo e outra gravando a mesma variável, sem nada que impeça os dois acessos de acontecerem ao mesmo tempo, é uma race condition. É um fato sobre os acessos.
  • Interferência é o resultado errado que pode sair disso (lição 1). É um fato sobre o resultado.

Uma coisa não implica a outra, e o material mostra os dois casos:

SituaçãoRace condition?Interferência?
getSaldo() sem synchronized, se saldo fosse intsimnão
Leitura e escrita em dois blocos synchronized separados (seção 6, a seguir)nãosim

No primeiro caso o slide diz que, com int, "não precisaria sincronizar: race condition que não implicaria em interferência"; como saldo é double, getSaldo foi marcado como synchronized. O segundo caso é a próxima seção.

Um terceiro uso, nos slides de Go, aponta no mesmo sentido: os channels evitam "condições de corrida (race conditions) ao garantir que apenas uma goroutine acesse dados por vez". Ou seja, race condition é sobre mais de uma thread acessando o mesmo dado ao mesmo tempo.

11-Concorrencia.pdf, slides 16 e 19; 09c-Go.pdf, slide 6. A distinção acima é uma leitura do uso do termo nesses três slides; nenhum deles traz uma definição formal.

6. A armadilha: sincronizar os pedaços errados

O material mostra uma versão que parece segura e não é:

void creditar(double vc) {
  double tmpc;
  synchronized(this) { tmpc = saldo; }     // leitura protegida
  tmpc = tmpc + vc;
  synchronized(this) { saldo = tmpc; }     // escrita protegida
}

Cada acesso a saldo está dentro de um bloco sincronizado, então nunca há duas threads lendo ou gravando saldo no mesmo instante. Mesmo assim, entre a leitura e a escrita de uma thread, a outra pode fazer um ciclo completo. O veredito do material: não há race conditions, mas pode haver interferências. O que precisa ser protegido é a sequência ler-calcular-gravar inteira, não cada acesso isolado.

11-Concorrencia.pdf, slide 19.

7. Como criar execução concorrente em Java

O operador || que usamos nas lições não existe em Java. O que existe são threads: sequências ou fluxos de execução que podem ser executados concorrentemente. Os comandos a executar são "empacotados" como objetos da classe java.lang.Thread.

A receita tem três partes.

(a) Empacotar o comando. Uma subclasse de Thread redefine o método run; o corpo de run é o que a thread vai executar.

class Credito extends Thread {
  private Conta conta;
  private double val;
  Credito(Conta c, double v) {
    conta = c; val = v;
  }
  public void run() {
    conta.creditar(val);
  }
}
class Debito extends Thread {
  private Conta conta;
  private double val;
  Debito(Conta c, double v) {
    conta = c; val = v;
  }
  public void run() {
    conta.debitar(val);
  }
}

(b) Criar e iniciar. start() inicia a execução da thread. (c) Esperar. join() espera pelo término da thread. Assim, A || B corresponde a:

Thread a = new ThreadA(...);
Thread b = new ThreadB(...);
a.start(); b.start();
try {
  a.join(); b.join();
} catch (InterruptedException e) { ... }

A frase do material para guardar: execução concorrente = criação e início de threads.

11-Concorrencia.pdf, slides 21–26.

8. Quando herdar de Thread é um problema

Se a classe já herda de outra, use a interface Runnable: implemente run do mesmo jeito e embrulhe o objeto em um Thread na hora de criar.

class Debito implements Runnable {
  private Conta conta;
  private double val;
  Debito(Conta c, double v) {
    conta = c; val = v;
  }
  public void run() {
    conta.debitar(val);
  }
}
Thread c = new Credito(...);   // subclasse de Thread
Thread d;
d = new Thread(new Debito(...)); // Runnable
c.start();
d.start();
try {
  c.join(); d.join();
} catch (InterruptedException e) { ... }

11-Concorrencia.pdf, slides 27–28.

9. Exemplo resolvido: a Conta com threads de verdade

Juntando as seções 3 e 7, este é um programa completo que compila e roda. Ele está em code/0002/ContaThreads.java. Para a interferência aparecer na prática, cada thread repete a operação 100 000 vezes com valor 1. Sem interferência, o saldo final é 0.

class Conta {
  private double saldo = 0;

  synchronized void creditar(double vc) {
    double tmpc = saldo;
    tmpc = tmpc + vc;
    saldo = tmpc;
  }

  synchronized void debitar(double vd) {
    double tmpd = saldo;
    tmpd = tmpd - vd;
    saldo = tmpd;
  }

  synchronized double getSaldo() { return saldo; }
}

class Credito extends Thread {
  private Conta conta;
  private double val;
  Credito(Conta c, double v) { conta = c; val = v; }
  public void run() {
    for (int i = 1; i <= 100000; i++) conta.creditar(val);
  }
}

class Debito extends Thread {
  private Conta conta;
  private double val;
  Debito(Conta c, double v) { conta = c; val = v; }
  public void run() {
    for (int i = 1; i <= 100000; i++) conta.debitar(val);
  }
}

public class ContaThreads {
  public static void main(String[] args) {
    Conta c = new Conta();
    Thread cr = new Credito(c, 1);
    Thread db = new Debito(c, 1);
    cr.start(); db.start();                 // creditar || debitar
    try {
      cr.join(); db.join();
    } catch (InterruptedException e) {}
    System.out.println("--> saldo final: " + c.getSaldo());
  }
}

Questão da prova: 2026-1, questão 4 (com resposta)

Questão 4 (1 ponto). Em Java, ao executar um método synchronized de uma classe, o que acontece se uma thread tentar chamar outro método, também synchronized, da mesma classe?

Resposta: "O thread solicitante fica em estado de espera até que o lock do objeto seja liberado."

Só um método synchronized executa por vez num objeto; a outra thread espera, seja o mesmo método ou outro (11, s.14 e 29). As outras alternativas: o objeto não é clonado; os métodos não executam ao mesmo tempo por serem diferentes; e não há exceção. Repare que a prova diz "da mesma classe" e o material diz "do mesmo objeto": a alternativa certa fala em "lock do objeto".

Respostas da recuperação inicial: (1) tmp = saldo; tmp = tmp + 5; saldo = tmp. (2) 1 A 2 3 B C dá −80; A 1 2 B C 3 dá 100. (3) O interpretador, de forma arbitrária.
