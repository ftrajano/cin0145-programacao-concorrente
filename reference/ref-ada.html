Tasks e rendezvous: como ler o código dos slides (08-Ada.pdf, "s.N" = página do PDF). Lição completa: Lição 7.

Em uma frase. Processos são tasks; elas se comunicam por rendezvous: comunicação síncrona, sem buffer, em que a primeira a chegar espera a outra (s.3, 9). Na questão 5 de 2026: síncronas: sim · rendezvous: sim · assíncronas: não · monitores: não.

Uma task tem duas partes

task Buffer is                        -- specification: o que a task oferece
  entry Append (I: in Integer);
  entry Take (I: out Integer);
end Buffer;

task body Buffer is                   -- body: o código
begin
  …
  accept Append(I: in Integer) do
    … corpo do accept
  end Append;
  …
end Buffer;

s.4–6. Entries ficam na specification; accept fica no body.

Rendezvous, passo a passo (s.7)

  1. A calling task chama Buffer.Append(I), passa os parâmetros in e espera.
  2. A accepting task executa o corpo do accept, até o end.
  3. Os parâmetros out voltam para a calling task.
  4. Fim do rendezvous: as duas seguem.

Quem chega primeiro espera o outro. A calling task precisa saber o nome da accepting task e da entry; a accepting não precisa saber quem chama: identificação assimétrica, bom para servidores (s.3–4, 9).

select com guardas

select
  when Count < N =>              -- guarda: só abre se houver vaga
    accept Append(I: in Integer) do B(In_Ptr) := I; end Append;
    Count := Count + 1;
or
  when Count > 0 =>              -- só abre se houver item
    accept Take(I: out Integer) do I := B(Out_Ptr); end Take;
    Count := Count - 1;
end select;
  1. Avalia as guardas when → conjunto de alternativas abertas. Precisa haver ao menos uma, ou um else.
  2. Se há tasks na fila de alguma entry aberta → rendezvous com a primeira de uma das filas (o slide não diz qual fila).
  3. Se todas as filas abertas estão vazias → a accepting task suspende até chegar uma chamada; as alternativas abertas não mudam enquanto isso.
  4. A última alternativa pode ser else …, delay T … ou terminate.
